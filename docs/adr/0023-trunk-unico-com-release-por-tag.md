# Trunk único na `main`, com release e release candidate por tag

Os branches `develop` e `staging` são descontinuados. A `main` passa a ser o trunk — o branch de desenvolvimento, o default do repositório e o único de vida longa —, protegida por regra que exige pull request e aprovação do check `Docker Compose Validate / test`. Todo trabalho passa a acontecer em branch efêmero criado a partir dela, tipicamente um por sprint, deletado no merge. A versão deixa de ser derivada do branch e passa a ser derivada da tag: um commit apontado por `vX.Y.Z` vale `X.Y.Z`, por `vX.Y.Z-rc.N` vale `X.Y.Z-rc.N`, e qualquer outro commit carrega o sufixo `-dev` sobre o `version.base`. O release candidate, que existia como branch, passa a existir como tag de pré-release publicada no GHCR sem mover o `latest`.

A decisão nasce da constatação de que o modelo de três branches cobrava a cerimônia de duas promoções por release sem entregar nenhuma das três garantias que justificavam sua existência. **O release candidate nunca existiu como artefato:** em treze tags de histórico não há uma única pré-release, e nenhuma GitHub Release marcada como tal — o `staging` produzia a string de versão `X.Y.Z-rc.N` num branch que só o mantenedor executava, de modo que ninguém, em nenhum momento, conseguiu baixar e validar um candidato. **A `main` nunca esteve protegida:** a API de branch protection responde 404 e a lista de rulesets é vazia, o que reduz a regra "somente via PR de `staging`, nunca commitar direto" a uma convenção escrita — contornada em 15/08/2026 pelo commit `4b87fbe`, feito direto na `main`, sem PR e fora da convenção de mensagens, para trocar um screenshot. **E o `staging` não filtrava nada:** o aceite manual no browser, que é o gate real de qualidade, acontece antes do primeiro merge; quando o código chegava ao branch de release já havia sido aceito, e a CI apenas repetia pela terceira vez um resultado verde.

O que tornou a mudança possível sem perda de segurança foi um pré-requisito que já estava satisfeito havia dois meses sem ter sido notado: desde o commit `8556484`, de 18/06/2026, o `docker-compose-validate.yml` executa `./gradlew test` em push e em pull request. O gate automatizado existia; faltava colocá-lo no caminho do merge. Some-se a isso que todo o pipeline de distribuição já era acionado por tag — `publish-image.yml` dispara em `push: tags: v*`, deriva a versão da própria tag e aplica `latest` apenas a tags sem hífen, lógica escrita antecipando pré-releases que nunca foram criadas — e o desenho de branches revela-se ortogonal ao que o usuário final consome.

## Considered Options

- **Manter os três branches** — descartado por cobrar duas promoções, dois merges e um ajuste de `version.rc` por release para produzir o mesmo artefato que uma tag produz sozinha, e por já estar sendo contornado na prática pelo próprio mantenedor no caso de mudanças triviais.
- **Manter `develop` + `main`, matando apenas o `staging`** — foi a recomendação inicial, feita sob a premissa equivocada de que a CI não rodava testes e de que a `main` protegida ainda pagava seu custo. Descartada quando os dois fatos se mostraram falsos: sem a proteção, a `main` era apenas um espelho atrasado do `develop`, e o par de branches gastava um merge por release para manter dois nomes apontando para o mesmo código.
- **Manter `staging` + `main`, matando o `develop`** — descartado por ser o `develop` renomeado: o branch de trabalho diário deixaria de ser o default do repositório, o visitante do GitHub e o contribuidor externo cairiam num branch permanentemente atrasado, e o nome "staging" leria como ambiente de homologação para quem chega de fora. Continuaria, além disso, sem produzir release candidate, porque candidato não vem de branch.
- **Trunk único com push direto, sem PR obrigatório** — é o desenho usual do trunk-based para um mantenedor solo e foi a primeira proposta, mas descartado por decisão explícita de preparar o projeto para múltiplos colaboradores antes que eles cheguem. Sem PR, a CI reporta depois do merge e um commit quebrado permanece na `main` até ser corrigido; com PR obrigatório, o mesmo check barra antes, e a transição para um time exige mudar um único parâmetro — aprovações requeridas de zero para um.
- **Squash como estratégia de merge padrão** — descartado por medição do histórico real: os commits do projeto já são entregas coesas com mensagem descritiva, sem o ruído de `wip` e `fix typo` que o squash existe para absorver, e uma sprint produz cerca de 2,4 deles. Colapsar uma feature, um bugfix e um chore de configuração numa entrada só destruiria o `git blame` em troca de esconder aproximadamente dez merge commits a cada sessenta dias. O squash fica habilitado no repositório, disponível caso por caso para PR externo com histórico ruidoso.
- **Branch de release permanente para estabilizar em paralelo ao desenvolvimento** — descartado por ser resposta a um problema que a cadência do projeto não tem: oito releases em cinco semanas não deixam janela para desenvolver a versão seguinte enquanto a atual estabiliza. Quando o caso aparecer, o branch `release-X.Y` é criado sob demanda a partir da tag, como fazem Kubernetes e Spring Boot.
- **Manter o filtro de `paths` no workflow que vira required check** — descartado por ser armadilha conhecida: um workflow filtrado simplesmente não reporta em pull request que não toca seus caminhos, e um check requerido que nunca reporta bloqueia o merge indefinidamente. O `docker-compose-validate.yml` perde o filtro e passa a rodar sempre, ao custo de três minutos; o `setup-script-validate.yml`, que provisiona cluster em dois runners e leva seis, mantém o filtro e por isso não pode ser requerido.

## Consequences

- A `main` passa a conter o histórico de desenvolvimento, não apenas releases. Ela parecia limpa porque o trabalho vivia no `develop`, que deixa de existir — o histórico não vira ruído por ficar visível no lugar onde as pessoas olham. Quem quiser a visão resumida por sprint tem `git log --first-parent`, que lista apenas os merges e devolve exatamente a granularidade que o squash daria, sem descartar a fina.
- O tip da `main` passa a ser trabalho em andamento, e isso alcança usuários reais por uma via específica: em `arm64` o `setup.sh` sempre compila do código-fonte, porque não há imagem publicada para essa arquitetura (ADR 0019). O Quick Start do README passa a instruir checkout da última tag antes de rodar o wizard. Em `amd64` nada muda, já que o script puxa `ghcr.io/greencapk8s/platform:latest` e ignora o código-fonte da árvore.
- Publicar uma imagem `arm64` eliminaria essa consequência pela raiz e tornaria o checkout de tag uma recomendação em vez de uma necessidade. Fica em aberto, e reabre o ADR 0019.
- O release candidate passa a ser distribuível pela primeira vez. Tagear `vX.Y.Z-rc.N` publica `ghcr.io/greencapk8s/platform:X.Y.Z-rc.N` sem tocar no `latest`, e qualquer pessoa valida com `PLATFORM_IMAGE_TAG=X.Y.Z-rc.N ./setup/setup.sh`. Nenhuma mudança de código foi necessária para isso: a capacidade já existia no `publish-image.yml` e no `setup.sh`, inerte por falta de uma tag.
- O bump de `version.base` deixa de ser consequência de um merge e passa a ser passo obrigatório logo após a tag de release. Esquecê-lo faz os commits seguintes saírem como `X.Y.Z-dev`, string que aparenta ser anterior ao `X.Y.Z` já publicado.
- `version.rc` desaparece do `gradle.properties` e a detecção de branch desaparece do `build.gradle.kts`. A derivação de versão fica reduzida a três casos em cadeia — variável de ambiente, tag exata, sufixo `-dev` — e passa a aplicar a mesma regra que o `setup.sh` já aplicava ao construir localmente: só tag exata conta como release, qualquer outro checkout é código em fluxo.
- A detecção de tag usa `git describe --tags --exact-match` com o stderr descartado. Dobrar o stderr sobre o stdout, como fazia a implementação anterior, transformaria a mensagem `fatal: no tag exactly matches` numa string de versão válida aos olhos do Gradle.
- Os workflows de validação deixam de rodar em três branches e passam a rodar apenas na `main` e nos pull requests que a têm como alvo. O mesmo commit deixa de ser testado cinco vezes por release.
- Contribuição externa fica com um alvo só. O `CONTRIBUTING.md` e o template de PR pediam `develop`; quem chegasse pelo default branch mirava no lugar errado por construção.
- A proteção nasce com zero aprovações requeridas, porque o GitHub não permite que o autor aprove o próprio pull request e o projeto tem um mantenedor. Enquanto for assim, a barreira é a CI, não a revisão humana — o modo de contornar acidentalmente a intenção da regra é abrir e mesclar sem ler o próprio diff.
